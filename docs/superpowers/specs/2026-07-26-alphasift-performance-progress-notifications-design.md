## 1. 背景与问题

当前选股已经通过后台任务运行，页面刷新或切换后也可以恢复任务，但仍存在三个连续问题：

1. **性能不可解释**：全市场快照、策略过滤、LLM 重排和 DSA 候选增强的阶段耗时没有结构化记录，无法确认真正瓶颈。
2. **等待过程近似黑盒**：任务主要在 20% 和 90% 更新，20% 长时间不动既不代表真实完成比例，也不能证明进程仍有活动。
3. **完成提醒不完整**：项目已有多渠道通知基础设施，但选股完成/失败没有接入；Web 没有浏览器通知，Electron 也没有原生系统通知桥。

三个问题存在依赖关系：

```text
阶段计时与性能事件
    -> 可解释的进度/心跳/活动时间线
        -> 基于可靠终态事件发送一次完成通知
```

因此必须按照“性能优化 → 等待体验优化 → 系统通知”推进，不能先用虚假的百分比或定时通知掩盖运行契约缺失。

## 2. 目标与非目标

### 2.1 目标

1. 建立可复现的阶段耗时基线，先测量再并发或缓存。
2. 降低候选后置增强的墙钟时间，同时保持数据源 timeout、fallback 和部分成功语义。
3. 让用户看到当前阶段、已运行时长、最近活动、处理数量和降级状态。
4. 任务长时间没有新业务事件时仍发送轻量心跳，明确区分“运行中”和“疑似停滞”。
5. 在用户明确授权后支持：
   - Web 浏览器系统通知；
   - Electron 原生系统通知；
   - 可选的既有远程通知渠道。
6. 保持同步 `/screen` 和后台 `/screen/tasks` 的结果契约兼容。

### 2.2 非目标

- 不修改 AlphaSift 策略算法、因子权重或投资结论。
- 不为了追求速度跳过 LLM、行情、基本面或新闻而不告知用户。
- 不把估算进度展示成精确完成比例。
- 不展示模型隐藏推理、完整 prompt、密钥、私有 URL、请求头或供应商原始响应。
- 不默认申请浏览器通知权限，不在页面加载时弹权限框。
- 不默认把选股结果发送到远程渠道。
- 不引入新的外部队列、缓存服务或数据库迁移。
- 本轮不实现任务强制取消；取消需要单独定义数据源和 LLM 的协作中止契约。

## 3. 当前链路与主要瓶颈假设

一次后台选股包含：

```text
请求校验
  -> 等待共享线程池
  -> AlphaSift 全市场快照
  -> 策略过滤与本地评分
  -> LLM 候选重排（可降级）
  -> 规范化结果
  -> 前 3 名 DSA 增强
       -> 名称
       -> 实时行情
       -> 基本面
       -> 新闻
  -> 序列化与终态
```

当前已知约束：

- 后置 DSA 增强按候选串行执行。
- 单个候选的行情、基本面、新闻大部分按顺序等待。
- `max_results=3` 时，LLM 仍可能评估最多 6 个候选。
- AlphaSift runtime 环境使用进程级锁保护临时环境变量和 monkey patch；并发选股任务可能在此处串行等待。
- 共享任务队列默认还承载普通股票分析，选股任务会与其它任务争用 worker。
- 外部数据源、LLM 和新闻服务的耗时波动较大，单次截图不能作为性能结论。

以上均是待基线验证的瓶颈假设，不在无测量证据时直接改并发度或锁。

## 4. 总体设计

### 4.1 三阶段交付

| 阶段 | 交付 | 进入下一阶段的门槛 |
| --- | --- | --- |
| Phase 1 | 阶段计时、性能基线、受控并发/复用优化 | 性能证据完整；结果、降级和资源无回归 |
| Phase 2 | 结构化活动事件、心跳、真实阶段 UI、停滞提示 | 后台恢复、轮询/SSE、可访问性和错误态通过 |
| Phase 3 | Web、Electron、远程渠道的完成/失败通知 | 去重、权限、隐私、失败隔离通过 |

每个 Phase 独立 review、独立验证，建议独立 PR。Phase 2 不应夹带新的性能策略，Phase 3 不应修改选股结果。

### 4.2 单一事件来源

服务层产生结构化运行事件，任务队列负责保存有限快照并广播，API 负责序列化，Web/桌面只负责展示或通知。

```text
AlphaSiftService / endpoint progress reporter
        -> TaskQueue.update_task_activity()
            -> TaskInfo current stage + bounded recent events
            -> existing SSE broadcast
            -> polling status response
                -> Web activity timeline
                -> desktop/browser terminal notification
```

不允许前端根据等待秒数自行伪造“正在调用 LLM”等业务阶段。

## 5. Phase 1：性能观测与优化

### 5.1 阶段计时契约

后台选股至少记录以下阶段：

| `stage` | 含义 | 可公开字段示例 |
| --- | --- | --- |
| `queued` | 等待 worker | `queue_wait_ms` |
| `snapshot` | 获取市场快照 | 数据源、已知快照数量 |
| `filter` | 策略过滤/评分 | 过滤后数量 |
| `llm_rank` | LLM 重排 | 候选数量、成功/降级，不含 prompt |
| `normalize` | 结果规范化 | 候选数量 |
| `enrich` | DSA 后置增强 | 当前候选序号、总数、成功/部分失败 |
| `finalize` | 整理响应 | warning/source error 数量 |
| `completed` / `failed` | 终态 | 总耗时、脱敏失败摘要 |

每阶段内部使用单调时钟计算 `duration_ms`，墙钟只用于用户可读时间和心跳。阶段计时写入任务运行时诊断和最终结果的可选 `timings` 字段；新增字段必须保持向后兼容。

如果当前 AlphaSift adapter 无法提供 `snapshot/filter/llm_rank` 回调，第一步只能把其整体标记为 `alphasift_screen`，并通过正式 adapter contract 增加可选 progress callback。不得靠解析日志字符串构造阶段。

### 5.2 基线方法

在同一机器、同一拓扑、相近数据快照下记录：

- 策略：`dual_low` 和一个 LLM 候选较多的策略；
- 参数：`market=cn`、`max_results=3`；
- 每个策略至少 1 次冷运行 + 3 次暖运行；
- 总耗时、各阶段耗时、快照数量、过滤后数量、LLM 调用次数、增强成功数；
- Python 峰值内存、外部请求数或可观测近似值；
- 单任务和两个同时提交任务的排队/锁等待行为。

真实 LLM 与市场数据会波动，因此优化前后比较必须保留相同参数和运行环境，并同时提供确定性 mock benchmark。

### 5.3 第一优先级优化：候选增强受控并发

候选增强改为有界并发，建议默认最大并发为 `min(3, candidate_count)`：

- 每个候选保持独立结果与 warning。
- 输出顺序仍按原始 rank，不按完成顺序改变。
- 一个候选或一个数据源失败不能取消其它候选。
- 遵守现有基本面预算、数据源 timeout、fallback、缓存和线程安全边界。
- 不复用可变 candidate 对象跨线程写入；worker 返回独立结果，主线程按 index 合并。
- DataFetcherManager、SearchService 或 provider 若不具备线程安全证据，则对应调用保持串行或使用更低并发。

候选内部的行情、基本面和新闻并行属于第二步，只有候选级并发证据不足且依赖线程安全验证通过后才实施。

### 5.4 缓存策略

优先复用已有行情、历史数据和基本面缓存。新增缓存前必须证明：

- 数据抓取在同一短窗口内被重复执行；
- key 包含市场、策略及影响结果的必要参数；
- TTL 不会把交易时段数据长时间陈旧化；
- failure/empty 不被长时间负缓存；
- 缓存命中在结果和诊断中可见。

第一轮不默认缓存最终 LLM 选股结果，避免把过期市场判断误当成新运行。

### 5.5 runtime 锁与任务队列

进程环境锁保护跨请求配置隔离，不能直接删除。优化顺序：

1. 测量 `lock_wait_ms`。
2. 优先推动 adapter 接收显式 context/config，减少依赖进程环境。
3. 只有 adapter 不再读取临时全局环境且 monkey patch 生命周期安全后，才缩小锁范围。
4. 不通过增加 `MAX_WORKERS` 掩盖锁竞争或触发数据源限流。

选股专用 executor/队列只在证明共享 worker 导致明显饥饿后另行设计，本 Spec 不默认引入。

### 5.6 性能验收

Phase 1 必须满足：

- 结果字段、候选顺序、降级语义与现有契约一致。
- 确定性 benchmark 中，3 个候选的后置增强墙钟时间较串行基线降低至少 30%。
- 真实环境提供前后数据；总耗时目标为暖运行中位数降低 20%，若瓶颈完全位于不可并发的 AlphaSift/LLM 阶段，则允许未达目标，但必须用 timings 证明并形成下一步决策，不能宣称性能目标完成。
- 峰值内存无不可解释增长，外部请求数不因重试/并发重复放大。
- 两任务并发不发生环境、header、candidate 或诊断串线。
- 单个数据源超时仍能部分成功或明确降级。

## 6. Phase 2：等待体验与活动可见性

### 6.1 任务活动契约

在现有 `progress/message` 上追加兼容字段：

```json
{
  "stage": "enrich",
  "stage_label": "正在补充候选信息",
  "progress_mode": "indeterminate",
  "started_at": "2026-07-26T10:00:00+08:00",
  "last_activity_at": "2026-07-26T10:01:12+08:00",
  "elapsed_ms": 72000,
  "metrics": {
    "current": 1,
    "total": 3,
    "candidate_count": 3
  },
  "recent_events": []
}
```

规则：

- `stage` 是稳定机器字段；`stage_label` 是可本地化显示文本。
- `metrics` 只允许白名单、非敏感标量。
- `recent_events` 最多保留 20 条；同类高频事件合并，防止内存和 payload 无限增长。
- 原有 `progress/message` 保留，旧客户端继续工作。
- 无可靠总量时使用 `progress_mode=indeterminate`，不显示误导性的精确百分比。
- 只有已知总量的子阶段，例如“增强 1/3”，才显示局部进度。

### 6.2 活动事件等级

活动事件分为：

- `info`：开始获取快照、开始重排、开始增强。
- `success`：获得快照、过滤完成、某候选增强完成。
- `warning`：数据源 fallback、LLM 降级、某增强项失败。
- `error`：任务终止失败。
- `heartbeat`：业务阶段未变化，但 worker 仍在运行。

事件文案描述操作事实，不声称展示 Agent 思维过程。例如显示“正在请求 LLM 对 6 个候选重排”，不显示内部推理、prompt 或模型草稿。

### 6.3 心跳与停滞

- 后台任务 processing 时，每 15 秒更新一次 `last_heartbeat_at`，但不把每个心跳都追加到历史事件。
- 前端每秒本地更新“已运行 1分32秒”，不需要每秒请求后端。
- 最近心跳超过 45 秒：显示“暂未收到新活动，任务可能仍在等待外部服务”。
- 超过 90 秒：显示 warning 和“继续等待”说明，但不自动把任务判定失败。
- 真实失败只由后端终态决定。
- 页面卸载后停止本地 timer；任务继续在后端运行。

心跳实现必须确认 worker 线程卡在同步外部调用时仍能更新。若无法从同一 worker 发出心跳，应由任务队列监控器基于 future 状态产生，不为每个任务创建永久线程。

### 6.4 Web UI

选股页运行态改为：

- 当前阶段标题。
- 已运行时长和最近活动时间。
- indeterminate 活动条，或有真实分母时显示局部进度。
- 最近 5～8 条活动时间线，可展开查看更多。
- 快照数、过滤后数量、LLM 状态、增强 `current/total` 随事件逐步出现。
- warning 不覆盖运行状态；用户可同时看到“仍在运行”和“某数据源已降级”。
- 保留任务 ID、刷新恢复与任务不可恢复处理。

SSE 是优先实时通道；现有轮询继续作为断线 fallback。Phase 2 可以先复用轮询交付契约，再接入现有任务 SSE，不能要求只支持 SSE 的客户端。

### 6.5 等待体验验收

- 每个已知阶段都有单元测试和 API contract 测试。
- 20% 不再被展示成长期不变的精确总进度。
- 外部调用超过 60 秒时，用户仍能看到已运行时间、最后心跳和当前阶段。
- 刷新/切换页面后恢复当前阶段与有限活动历史。
- SSE 断开时轮询继续更新；重复事件不会重复插入时间线。
- 屏幕阅读器能获知阶段变化，但心跳不会高频打扰。
- 不泄露 prompt、密钥、URL query、headers 或原始异常堆栈。

## 7. Phase 3：系统通知

### 7.1 通知类型与默认值

分为三个独立能力：

| 类型 | 触发位置 | 默认 | 适用场景 |
| --- | --- | --- | --- |
| Web 系统通知 | 浏览器 Notification API | 关闭 | 页面在后台但浏览器仍运行 |
| 桌面系统通知 | Electron main process | 关闭 | 桌面应用最小化/后台 |
| 远程渠道通知 | 后端 NotificationService | 关闭 | 页面关闭后仍需收到提醒 |

三个开关独立，不能因为用户配置了报告通知就自动发送选股结果。

### 7.2 权限与设置

- 只有用户点击“开启系统通知”后才请求浏览器权限。
- `denied` 时展示浏览器设置指引，不重复弹权限请求。
- Electron 通过受限 preload IPC 调用 main process 的 `Notification`；renderer 不能传任意 HTML、图标路径或 shell URL。
- Web 偏好可先存本地存储；远程通知属于服务端行为，必须使用明确配置项，并同步 `.env.example`、设置页和文档。
- 多 tab 中同一任务只通知一次，使用 `task_id + terminal_status` 去重；本地去重有 TTL。

### 7.3 触发与内容

只在终态触发：

- 完成：标题、策略/市场、候选数量、总耗时、查看提示。
- 失败：标题、策略/市场、脱敏失败摘要。

不在通知中包含完整候选理由、持仓信息、prompt、密钥或外部错误详情。点击本地通知只聚焦应用并导航到选股页；不得自动交易、写入自选股或打开未经校验的远程 URL。

### 7.4 后端远程通知

- 新增独立 route type 或明确的选股事件路由，不复用 `report` 后隐式扩大通知范围。
- 通知发送发生在任务终态落定之后。
- 发送失败只记录诊断，不能把成功选股改成失败。
- 重试必须带幂等键，避免 worker 重试或服务恢复时重复发送。
- 结果只发送摘要；是否附候选代码需要在 review 中明确，默认不附。

### 7.5 通知验收

- 未授权、denied、不支持 Notification API 时不报错、不发送。
- 前台页面默认不弹系统通知；可由设置决定是否“仅后台通知”。
- 完成和失败各只发送一次。
- 刷新、SSE 重连、轮询重复终态不会重复通知。
- Electron IPC 输入经过长度、类型和来源限制。
- 远程渠道未配置或发送失败不影响任务结果。
- 通知内容通过敏感信息回归测试。

## 8. API 与数据兼容

- `AlphaSiftScreenTaskStatus` 只追加可选字段。
- `AlphaSiftScreenResponse` 可追加 `timings`，旧客户端忽略即可。
- 同步 `/screen` 继续可用，但不提供后台心跳或恢复；Web 继续使用 `/screen/tasks`。
- TaskInfo 的新字段必须有默认值，普通股票分析任务不需要立即产生同一套 AlphaSift 阶段。
- SSE 事件继续使用现有任务事件类型；payload 追加字段，避免创建第二套不兼容流。
- 不新增数据库 schema；进程重启后任务和活动历史仍按当前语义不可恢复。

## 9. 测试与验证矩阵

### 后端

- 阶段计时使用可控时钟的单元测试。
- adapter progress callback 支持与旧 adapter 无 callback 的兼容测试。
- 候选并发：顺序稳定、部分失败、timeout、warning 聚合、线程安全测试。
- TaskInfo copy/to_dict、bounded events、心跳、终态竞争和 SSE payload 测试。
- 通知幂等、失败隔离、路由与脱敏测试。

### Web

- 阶段、indeterminate、局部进度、elapsed、stale heartbeat 和恢复测试。
- SSE + polling fallback、事件去重测试。
- Notification permission 的 default/granted/denied/unsupported 测试。
- 多 tab/重复终态去重测试。
- lint、build 和选股页截图。

### Desktop

- preload 只暴露受限通知方法。
- main process 的支持检查、输入校验、点击聚焦和失败测试。
- Web build 后再执行 Electron build。

### 真实验证

- 两种策略基线与优化后对照。
- 一个慢数据源/LLM 场景，确认阶段、心跳和降级。
- 浏览器后台完成通知。
- 桌面最小化完成通知。
- 一个远程测试渠道的成功与失败隔离。

## 11. 风险与回滚

### 风险

- 并发增加上游限流或触发非线程安全 provider。
- 过细事件造成锁竞争、SSE 噪声和 payload 膨胀。
- 心跳被误认为业务仍有实质进展。
- 浏览器权限体验打扰用户。
- 多 tab、SSE 重连和轮询导致重复通知。
- 远程通知内容扩大隐私暴露面。

### 控制

- 有界并发、保持 timeout/fallback、先 mock benchmark 再真实 smoke。
- bounded events、节流、白名单 metrics。
- UI 区分“最近业务活动”和“进程心跳”。
- 权限只由用户手势触发，所有通知默认关闭。
- 以任务终态和幂等键去重。
- 默认只发送摘要。

### 回滚

1. Phase 3：关闭本地通知偏好及选股远程通知配置，不影响任务。
2. Phase 2：前端退回 `progress/message` 展示；后端追加字段可保留。
3. Phase 1：关闭新增并发开关或恢复并发数 1；计时观测可保留。

无数据库迁移，回滚不需要数据修复。

## 12. Review 决策点

建议本轮 review 确认以下默认方案：

1. 接受三阶段、建议三个独立 PR 的交付边界。
2. Phase 1 首先只做“候选级最大并发 3”，候选内部并发以证据决定。
3. 无真实分母的阶段不显示总体百分比，改用 indeterminate + 阶段 + elapsed。
4. 心跳 15 秒、45 秒提示延迟、90 秒 warning。
5. 活动历史后端最多保留 20 条，页面默认显示最近 5～8 条。
6. Web、桌面、远程通知全部默认关闭并分别授权。
7. 本地系统通知默认仅在页面不可见或桌面窗口非前台时发送。
8. 远程通知默认只发送摘要，不附候选代码。
9. 任务取消不进入本轮范围。
